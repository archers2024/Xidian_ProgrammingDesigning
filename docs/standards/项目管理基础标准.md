# 项目管理基础标准

适用项目：高校学生活动全流程管理系统。

本文件用于约束人工与 AI 的文件管理、模块组织和交付方式。AI 在创建或调整项目文件前必须先阅读本文件，并按下列分类存放文件。用户明确要求优先；未明确的日常组织方式按本标准执行。

规范版本：1.0。制定日期：2026年10月18日。

## 1 基本原则

1. 文件按用途归类，同一种用途有固定归属目录。
2. 先找现有文件，再决定新增；先复用现有模块，再决定新增模块。
3. 一个事实维护一个权威来源，代码、SQL、接口文档不复制多份。
4. 源码、文档、运行数据、临时产物和交付压缩包分开存放。
5. 修改只覆盖本次任务，不顺手进行全项目移动、改名、格式化或重构。
6. 目录按实际需要创建，禁止为了“结构完整”生成整套空目录。
7. 以下目录树为目标组织方式，未开始的模块可以不存在。

## 2 项目根目录标准

```text
项目根目录/
├── AGENTS.md                  AI 读取入口与强制规则
├── README.md                  项目说明、环境、启动和导航
├── .gitignore                 忽略运行数据与生成产物
├── .editorconfig              需要时添加的编辑器格式配置
├── backend/                   Java 后端工程
├── frontend/                  Vue 前端工程
├── database/                  达梦权威 SQL、初始化和变更脚本
├── docs/                      需求、方案、接口、设计、测试和报告
├── scripts/                   需要跨模块使用的维护脚本
├── deployment/                部署模板、代理配置和环境说明
├── artifacts/                 可重建的检查、截图和构建分析产物
├── runtime/                   上传文件、日志、本地运行配置
├── releases/                  最终提交压缩包等打包产物
└── .tmp/                      本次任务的临时文件
```

根目录只放项目级入口文件、确有需要的项目级配置，以及上述目录。不在根目录放业务源码、单独 SQL、下载文件、测试截图、实验脚本或新增方案文档。

当前已有的 `第二题_详细实现路线与前后端协作方案.md` 是历史例外，可原位维护。本次制定规范不迁移它。后续新增方案放 `docs/plans/`；如以后任务明确需要迁移，应移动并更新引用，不留两份继续编辑。

后端的 `pom.xml` 放在 `backend/`；前端的 `package.json` 和依赖锁文件放在 `frontend/`。只有确实采用多模块或工作区工具时，才增加有实际作用的根目录构建配置。

## 3 文件归属速查表

| 准备创建的内容 | 必须放置的位置 |
|---|---|
| Java 业务源码 | `backend/src/main/java/` 下对应业务包 |
| MyBatis 映射文件 | `backend/src/main/resources/mapper/` 下对应模块 |
| 后端公开配置 | `backend/src/main/resources/`，使用环境变量占位 |
| Java 测试 | `backend/src/test/java/` 下对应测试包 |
| 后端测试资源 | `backend/src/test/resources/` |
| Vue 页面 | `frontend/src/views/` 下对应使用端 |
| 可复用组件 | `frontend/src/components/` 下对应模块 |
| 前端接口调用 | `frontend/src/api/` |
| TypeScript 业务类型 | `frontend/src/types/` |
| 前端模拟接口 | `frontend/src/mocks/` |
| 路由与页面守卫 | `frontend/src/router/` |
| 共享前端状态 | `frontend/src/stores/` |
| 主题与通用动效 | `frontend/src/styles/` |
| 需要构建处理的图片和字体 | `frontend/src/assets/` |
| 必须保持固定 URL 的静态文件 | `frontend/public/` |
| 前端单元或端到端测试 | `frontend/tests/unit/`、`frontend/tests/e2e/` |
| 达梦建表、初始化、数据变更 | `database/dm/` |
| 需求和验收标准 | `docs/requirements/` |
| 实现路线和阶段计划 | `docs/plans/` |
| 正式接口契约 | `docs/api/openapi.yaml` |
| 架构、数据库、业务流程说明 | `docs/design/` |
| 前端设计规范和动效约定 | `docs/design/frontend-design.md` |
| 测试用例和结果记录 | `docs/testing/` |
| 阶段任务和联调问题 | `docs/progress/`，需要时创建 |
| 项目报告及正式报告导出文件 | `docs/report/` |
| 演示流程与答辩说明 | `docs/demo/` |
| 文档正式引用的截图和图示 | `docs/assets/images/` 下对应主题 |
| 通用维护脚本 | `scripts/` |
| Nginx、容器及部署配置模板 | `deployment/` |
| 调试截图、测试报告、性能采样 | `artifacts/` 下对应类型 |
| 活动封面和附件上传文件 | `runtime/uploads/covers/`、`runtime/uploads/attachments/` |
| 应用运行日志 | `runtime/logs/` |
| 本地私有配置 | `runtime/config/` 或对应工程忽略的本地配置 |
| 最终源码提交压缩包 | `releases/` |
| 临时提取、试验、转换文件 | `.tmp/` 下的本次任务目录 |

如果文件同时看起来属于多个位置，按“主要用途”和“唯一维护来源”决定，不重复存放。已有业务模块的具体组织优先沿用；新增模块按本文件的分类建立。

## 4 后端目录标准

后端按业务模块组织，再在模块内部区分层次。基础包名在工程创建时统一确定，例如 `com.campus.events`，后续不得混用多套基础包名。

```text
backend/
├── pom.xml
├── mvnw、mvnw.cmd、.mvn/             使用 Maven Wrapper 时添加
├── src/main/java/com/campus/events/
│   ├── auth/                        管理员认证
│   ├── activity/                    活动管理与发布
│   ├── registration/                报名
│   ├── checkin/                     签到与动态码
│   ├── attachment/                  封面及附件
│   ├── dictionary/                  类型与学院字典
│   ├── dashboard/                   统计概览
│   ├── common/                      确实跨模块使用的基础能力
│   └── config/                      框架配置
├── src/main/resources/
│   ├── application.yml
│   └── mapper/                      与业务模块对应的 MyBatis XML
├── src/test/java/                   与主代码包结构对应
├── src/test/resources/
└── target/                          自动生成，忽略提交
```

每个业务模块根据需要添加 `controller/`、`service/`、`mapper/`、`entity/`、`dto/`。不必为只有一个文件的简单模块预建所有层次。

- Controller 接收请求和组织响应；Service 保存业务规则与事务；Mapper 负责数据库访问。
- DTO 与数据库实体分开，公开响应不直接暴露数据库实体。
- 只在确有复用时放入 `common/`，不得把所有工具与业务代码都放进通用包。
- MyBatis XML 的 namespace 与 Mapper 接口对应，文件名一致。
- 全项目统一使用一种数据访问方式，不为个别页面随意再引入另一套 ORM。

## 5 前端目录标准

```text
frontend/
├── package.json
├── package-lock.json                以 npm 为例，只保留所选工具的锁文件
├── vite.config.ts
├── tsconfig*.json
├── index.html
├── public/
├── src/
│   ├── main.ts
│   ├── App.vue
│   ├── api/                         http.ts、admin/、public/
│   ├── types/                       activity.ts、registration.ts 等
│   ├── mocks/                       与正式接口同协议的模拟实现
│   ├── layouts/                     AdminLayout.vue、PublicLayout.vue
│   ├── router/
│   ├── stores/
│   ├── styles/                      tokens.css、global.css、transitions.css
│   ├── assets/
│   ├── components/
│   │   ├── common/
│   │   ├── activity/
│   │   └── checkin/
│   └── views/
│       ├── admin/                   登录、工作台、活动、签到大屏
│       └── public/                  宣传、报名、手机签到
├── tests/
│   ├── unit/
│   └── e2e/
├── node_modules/                    安装生成，忽略提交
└── dist/                            构建生成，忽略提交
```

- 页面文件放 `views/`，多个页面复用的组件放 `components/`。
- 页面不直接调用裸 `fetch` 或创建 Axios 实例，统一通过 `api/`。
- 模拟数据统一放 `mocks/`，不散落在页面和组件中。
- 接口类型放 `types/`；仅组件内部使用的简单类型可以留在组件文件中。
- 路由转场集中在布局与统一样式中维护，页面不各写一套互相冲突的切换逻辑。
- 同一项目只保留一种包管理器及其锁文件，不能同时提交 npm、pnpm、Yarn 三套锁文件。
- 前端工程的 `.env` 文件只放公开配置；任何 `VITE_` 变量均不得保存后端密钥或数据库密码。

## 6 数据库脚本标准

```text
database/
└── dm/
    ├── README.md                    执行顺序、适用版本与数据说明
    ├── schema.sql                   从零初始化的基线结构
    ├── seed-base.sql                必需字典和基础数据
    ├── seed-demo.sql                可选演示数据
    └── migrations/
        └── V001__add_example.sql    后续增量变更示例，不预先创建
```

1. 正式达梦 SQL 的权威来源是 `database/dm/`。不要同时在文档、根目录、后端资源中维护多份建表脚本。
2. 基线初始化与后续增量升级的执行方式写入 README，标明基线对应版本，避免重复执行同一变更。
3. 已应用的增量脚本不直接改内容，需要修正时新增下一版本。
4. 初始化数据和演示数据分离，不能启动应用时自动删除正式数据并重建演示库。
5. 演示数据使用虚构姓名和手机号，不提交真实人员信息或实际密码。
6. 如未来引入必须从后端资源目录读取 SQL 的迁移框架，先统一调整本规范与加载方式，保留唯一来源，不长期手工同步两份。

本条更新了早期实施路线中资源目录内 SQL 与提交目录内 SQL 的组织方式：功能路线保持不变，实际文件归属以本规范为准。

## 7 文档管理标准

- 需求与验收标准以 `docs/requirements/` 中的当前文档为准。
- 接口路径、字段、枚举和错误码以 `docs/api/openapi.yaml` 为权威来源。
- 实现路线放 `docs/plans/`，前端风格、架构、数据库设计放 `docs/design/`。
- `docs/progress/tasks.md` 用于确有需要的任务状态，`docs/progress/integration-issues.md` 用于联调问题；不按每次 AI 对话新建一份进度记录。
- 正式报告源文件及经过确认的导出稿放 `docs/report/`，调试渲染图片仍放 `artifacts/`。
- 文档截图放 `docs/assets/images/<主题>/`，例如 `docs/assets/images/testing/registration-success.png`。
- 文档内部使用相对链接，保证目录整体移动后仍可阅读；根目录入口链接从根目录计算。
- 更新同一份文档，不创建“最终版”“最终版2”“最新修订版”等副本。阶段记录确有保留价值时归档到 `docs/archive/` 并注明日期与替代关系。
- 不为一个低影响修复新增方案、日报和复盘；只同步确实变化的需求、接口或使用说明。

旧方案与本规范在目录命名上冲突时，以本规范为准；业务功能仍按已确认需求执行。用户本次明确指定的位置或流程优先于本规范。

## 8 命名与编码标准

| 对象 | 命名方式 | 示例 |
|---|---|---|
| 代码目录、模块 | 英文小写，必要时用短横线 | `checkin`、`activity-card` |
| Java 类与接口 | PascalCase | `ActivityService.java` |
| Java 方法与变量 | camelCase | `publishActivity` |
| Vue 页面及组件 | PascalCase | `ActivityList.vue`、`CheckinCountdown.vue` |
| TypeScript 模块 | 小写短横线或已有工程约定 | `activity.ts`、`checkin-session.ts` |
| Pinia Store | 明确业务名，风格统一 | `auth.ts` |
| 文档 | 中文描述或英文短横线，含义明确 | `项目管理基础标准.md`、`frontend-design.md` |
| 图片 | 英文小写短横线 | `activity-publish-preview.png` |
| 临时任务目录 | 日期加简短主题 | `.tmp/20261018-api-check/` |
| 数据库增量脚本 | 递增版本与描述 | `V002__add_checkin_index.sql` |

新增文本文件统一采用 UTF-8；换行符和缩进沿用现有工程，必要时由 `.editorconfig` 统一。不对无关文件批量更换编码或换行符。

禁止 `test2`、`aaa`、`新建文本文档`、`复制`、`backup-final` 等无语义命名。业务代码不得直接放在根目录，正式模块不得依赖 `.tmp/`、`artifacts/` 或 `releases/` 中的文件。

## 9 临时文件、运行数据与提交产物

| 目录 | 是否应进入源码版本控制 | 维护方式 |
|---|---|---|
| `backend/`、`frontend/src/` 等源码 | 是 | 正式维护 |
| `docs/`、`database/`、部署与维护脚本 | 是 | 内容与实际系统同步 |
| `node_modules/`、`target/`、`dist/` | 否 | 通过构建或安装重建 |
| `.tmp/` | 否 | 仅清理本次任务创建且确认可删除的内容 |
| `artifacts/` | 否 | 调试与验证输出，需要正式留证时挑选到文档资产目录 |
| `runtime/` | 否 | 含用户上传和运行配置，按实际数据备份，禁止当作缓存随意清空 |
| `releases/` | 否 | 由源码与文档打包生成，按提交需要保留 |

不要把数据库备份、上传文件、密钥、会话数据和完整运行日志混入源码目录。最终压缩包不包含 `node_modules`、构建缓存和私有配置，包含源码、锁文件、数据库脚本、配置模板和运行说明。

`.gitignore` 只阻止尚未跟踪的文件进入版本控制；若发现此前已跟踪敏感或生成文件，应单独说明并按任务范围修正，不能误以为新增忽略规则就已移除历史内容。

## 10 AI 新增文件前必须执行的流程

1. 明确本次任务属于前端、后端、数据库、文档、脚本还是部署。
2. 在对应目录中做针对性查找，确认是否已有可修改的同类文件。
3. 依据速查表确定路径，并确认当前任务允许修改该范围。
4. 如果目录不存在，只创建本次确实需要的目录。
5. 新增或修改文件，同时更新实际受影响的引用和入口。
6. 检查是否误引入重复源码、重复 SQL、根目录杂项、真实配置或生成产物。
7. 运行与修改相关的最小验证；普通文档修改不要求启动整个系统。
8. 简短报告修改路径和验证结果；未运行的检查说明原因。

已有文件位置不完全符合规范时，先在原位完成当前授权任务。只有当前任务需要迁移时才移动，并同步引用；不进行顺手整理。移动或删除前确认目标与影响，不覆盖同名文件，不删除他人未提交的修改。

## 11 协作和变更边界

- 默认职责为用户写后端、AI写前端，用户明确调整分工时按新分工执行。
- 前端发现接口缺失时，在现有接口或联调文档记录所需字段、错误码与影响，不自行伪造成功数据作为正式实现。
- 确认接口变化后，先更新契约，再调整调用和实现。
- 一个任务围绕一个清晰功能或问题，避免同一任务混入无关重构和依赖升级。
- 不自动执行 Git 提交、推送、合并或初始化仓库；用户要求时再执行。
- 用户要求创建可复用规范时修改本文件；只影响某个子目录的补充约定可以写入该目录的 `AGENTS.md`，并说明作用范围。

## 12 放置示例

```text
正确：新增报名页面
frontend/src/views/public/RegistrationPage.vue

正确：新增活动接口封装
frontend/src/api/admin/activity.ts

正确：新增动态二维码说明
docs/design/dynamic-checkin.md

正确：新增达梦索引变更
database/dm/migrations/V001__add_registration_index.sql

正确：保存一次手机调试截图
artifacts/screenshots/registration-mobile.png

正确：保存报告正式引用的截图
docs/assets/images/report/registration-mobile.png

错误：在根目录新增 RegistrationPage.vue、数据库最终版.sql、截图1.png
错误：把运行上传文件写入 frontend/public/uploads/
错误：把临时验证代码当作正式模块依赖

```

以上标准的执行目标是让后续 AI 能确定文件归属、维护唯一版本，并在不扩大任务范围的前提下持续开发。
